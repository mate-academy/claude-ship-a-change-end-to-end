# Notes — `PUT /users/:id`

**The plan I approved, and edits.** The plan was: add an `updateUser(id, { name, email })` helper to `db/store.js` that reuses the existing `getUserById` lookup and returns `undefined` when the id doesn't match, then add a `PUT /:id` route in `routes/users.js` that validates first (reusing the exact falsy check and error message `POST /` already uses), checks not-found second, and returns the updated user on success. I approved it as written — the only real decision was how strict validation should be, and I chose to match the existing `POST /users` pattern (reject on falsy `name`/`email`) rather than add extra type/format checks, to keep create and update consistent rather than inventing stricter rules for one endpoint but not the other.

**Model.** Sonnet 5. The feature was small and fully specified by the pre-written tests and an existing `POST /` handler to mirror — not a case that needed a heavier-reasoning model, just careful pattern-matching to the codebase.

**Commit split.** Two commits: the store helper first (`db/store.js`), then the route that depends on it (`routes/users.js`). Data layer before the layer that calls it, so each commit stands on its own and reads cleanly in isolation — the second commit's diff makes sense without needing to guess what `store.updateUser` does, since it was already introduced.

**What the review caught.** Checked the not-found path, the validation path, a non-numeric id (`PUT /users/abc` — coerces to `NaN`, `getUserById` finds nothing, returns a clean 404 rather than crashing), and whether partial updates should be allowed (no — `PUT` here is a full replace, matching the test that expects 400 when a field is missing). One thing I considered rather than "caught" as a bug: `updateUser` mutates the existing user object in place instead of building a new one. I kept it, since the store already hands out live references elsewhere (`getAllUsers`/`getUserById` aren't defensive copies), so in-place mutation is consistent with how the rest of the module already behaves. No blocking issues found.
